01 / 프로젝트 역할

검증 전 과정 전담

  • 요구사항 분석 · 테스트 설계Fault Detection·Recovery·Clear의 선행 조건, 경계값, Timing을 테스트 조건과 기대 결과로 구체화했습니다.
  • 검증 환경 구성 · CAPL 자동화CANdb·CANoe·Panel을 구성하고, 7개 고장 시나리오에 대해 Testcase 24개를 작성했습니다.
  • 결함 재현 · 분석 · 문서화Panel·CAN Trace 창을 통한 수동 검증과 CAPL 자동 검증의 결과를 비교했습니다. 기대 결과와 실제 결과를 대조해 재현 조건·영향도·개선 방향을 정리하고, 각 시험 결과와 요구사양 간 추적성을 확보했습니다.

02 / 트러블슈팅

수동·자동 검증의 판정이 달랐던 이유

  1. 문제 · 동일 조건에서 다른 판정동일한 Timing 조건임에도 수동 검증과 CAPL 자동 검증의 결과가 달랐습니다.
  2. 분석 · 측정 시작점을 추적CAN Trace Timestamp와 CAPL Flag를 비교해, 최신 Frame이 아닌 이전 Frame을 기준으로 시간 측정을 시작하는 것을 확인했습니다.
  3. 해결 · 최신 Frame에 동기화최신 Frame 수신을 확인한 후 타이머가 동작하도록 CAPL 로직을 개선했습니다.
  4. 재검증 · 경계값과 Timing 확인경계값·Timing 시나리오를 다시 실행했습니다. 측정 불확도와 수정 전후 정량 비교는 추가 검증 대상으로 남겼습니다.

01 / 프로젝트 역할

교육 예제 기반 구현·디버깅

  • 메모리 영역 · 진단 절차 이해제공된 Application Primary·Backup 영역과 UDS 리프로그래밍 예제를 분석하고 요구사항별 처리 흐름을 정리했습니다.
  • Embedded C · Flash 제어 구현제공된 MCAL·RTE 연결을 바탕으로 UDS 7개 서비스, Application Backup·Restore, SHA-256 비교 분기를 구현·수정했습니다.
  • Trace32 디버깅 · 재검증함수 인수·레지스터·Trap 정보를 대조해 정렬 위반을 특정하고, 버퍼 수정 후 양방향 복사와 해시 판정을 확인했습니다.

02 / 트러블슈팅

CAN 응답 중단의 원인은 메모리 정렬

  1. 문제 · Flash Backup 중 응답 중단RoutineControl의 EraseMemory 처리에서 EA_AppToBackup() 호출 이후 CAN 응답이 멈췄습니다.
  2. 분석 · 세 가지 주소를 교차 확인실패한 load 명령, 버퍼 주소와 Trap 정보를 대조해 홀수 주소의 word 접근을 특정했습니다.
  3. 해결 · 4바이트 정렬 보장uint32 저장 공간에 바이트 단위로 접근하도록 바꿔 복사 버퍼의 정렬을 확보했습니다.
  4. 재검증 · 양방향 복사와 해시 비교Application→Backup→Application의 Flash Write·Read와 SHA-256 판정을 다시 확인했습니다.
