PROJECT 02 · EMBEDDED SW DEVELOPMENT

OTA를 위한 Bootloader 설계 및
SW Binary 위변조 감지

개인 프로젝트 · 개발 중심

Infineon AURIX TC234LP 기반 ECU에서 업데이트 실패와 Binary 변경 상황에도 기존 애플리케이션을 보호하도록 UDS 리프로그래밍, Backup·Restore, SHA-256 무결성 검사를 연결했습니다.

유형
개인 프로젝트
수행 기간
2026.03.03–2026.03.24
팀 규모
1명
기여도
100%
담당 범위
설계·구현·디버깅·검증 전담
목표
불완전하거나 변경된 업데이트 이미지로의 부팅을 방지하고 정상 애플리케이션 복구 경로를 구성했습니다.
역할
부트캠프 개인 과제로, 제공된 AURIX·MCAL 교육 환경 위에서 메모리 영역과 진단 절차 설계, Embedded C 구현, Flash 제어, Trace32 디버깅을 전담했습니다.
구현
UDS 7개 서비스(0x10·0x27·0x31·0x34·0x36·0x37·0x11), Application Backup·Restore, SHA-256 비교와 실패 정책을 구현했습니다. 0x31은 EraseMemory·Backup과 CheckProgrammingDependencies 두 루틴에 사용했습니다.
검증
정상 다운로드, 전송 순서 오류, 무결성 불일치, 복구 경로와 양방향 Flash Write를 시나리오별로 확인했습니다.
결과
Memory Alignment Trap의 원인을 4바이트 정렬 조건으로 특정하고 수정 후 Application→Backup→Application 복구 흐름을 재검증했습니다.
근거 수준
결과 서술은 교육 당시 ECU에서 수행한 시나리오 시험 기록을 근거로 합니다. 현재는 TASKING·EB tresos와 대상 ECU가 없어 새 빌드나 하드웨어 재시험을 하지 않았고, 정렬 수정은 수정 전후 소스와 SHA-256 대조까지 확인했습니다. 케이스별 근거 수준은 TEST RESULTS에서 PASS · Not executed · Evidence unavailable로 구분했습니다.
범위·한계
교육 과정 범위의 구현으로, 고정 키를 접두어로 붙인 SHA-256 검사입니다. HMAC이나 전자서명이 아니므로 전송 오류와 단순 변조는 검출하지만 해시까지 다시 계산하는 공격자는 막지 못합니다. 실차 수준에는 보호된 키 기반 HMAC 또는 전자서명이 필요하며, 이 한계는 구현 후 정적 리뷰에서 직접 정리했습니다.

KEY RESULTS

UDS 7개 서비스 흐름 Session·Security·Download·Reset 연계
Backup·Restore Primary와 Backup 영역 간 복구 경로
SHA-256 Application Binary 무결성 판정
Trap 원인 해결 Trace32 기반 4바이트 정렬 수정
